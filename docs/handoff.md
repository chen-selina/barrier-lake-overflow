   預設就是馬太鞍溪同一窗格、2026-06～09，不用改參數。

3. 右側 Tasks 分頁逐一按 Run，匯出到 Google Drive，下載後全部放到 `data/raw/sentinel1/`。

4. 在 `code/` 底下執行（需要 numpy、rasterio、scipy，見 `requirements.txt`）：

   ```bash
   python scripts/run_sar_series.py --name neg2026_matai_an --lon 121.29752 --lat 23.70061 --pass-time 21:52 --scenario-name "馬太鞍溪 · 2026 汛期（負案例）" --kind negative
   ```

### 2. 外部證據換成官方原始出處

**為什麼**：事件卡上 7/24 光學影像、7/27 航拍、8/20 蓄水量、下游保全對象，目前出處是維基百科。被問「這是誰說的」時要能指向官方原文。

**步驟**

1. 找下列事實的官方原文（新聞稿、應變簡報），確認日期與數字：
   - 7/24 農村水保署以 Planet 光學衛星影像發現堰塞湖、成立應變小組
   - 7/27 林保署航遙分署航拍，推估崩塌量約 2 億 m³、壩高約 200 m
   - 8/20 官方估蓄水量 4,800 萬 m³、滿水位 9,100 萬 m³
   - 9/21 撤離範圍：光復鄉、鳳林鎮、萬榮鄉共 1,800 戶、8,000 多人
2. 改 `data/raw/scenarios/matai_an_2025.json` 裡 `externalEvidence` 與 `exposure` 的 `source`、`url`（日期或數字不同就一併改 `time`、`text`）。
3. 在 `code/` 底下跑 `python -m pipeline.events.build`，再跑 `python -m unittest tests.test_events` 確認通過。

**完成標準**：四筆出處都是官方網址；測試通過。

### 3. 簡報改新故事線

- 拿掉「7 秒運算」之類強調速度的說法。改講：跑完之後，值班人員能不能更快知道下一個該查什麼。

### 5. 準備問答

| 可能的問題 | 回答重點 |
|---|---|
| 如果判錯呢？ | 2025：4 個暗區都被複核排除，沒進高優先。2026 負案例：崩塌堆積區有 1 個約 1 公頃的誤報整季列高優先，光學查證確認不是水；但信心從未到「高」，值班人員看得出它只有 SAR 單一證據。這是已知失效情境：事件前地形看不到崩塌後的新地形 |
| 為什麼只有 SAR 時信心最高到「中」？ | 單一來源可能是陰影或濕土；要光學、航拍或人工查證等獨立證據才到「高」 |
| 4 km 窗格怎麼決定的？ | 回放是以事後登載的壩址為中心；實際值班應由崩塌熱區或雨量警戒區決定（已列在 README 已知限制） |
| 外部成果怎麼進來？ | 目前人工整理進情境檔，依時間與位置自動對到事件；之後可接機關的開放資料 |
| 參數怎麼來的？ | 坡度門檻 35°、追蹤半徑 250 m 都只用馬太鞍溪校準過，這是已知限制 |
| 跟政府既有系統有什麼不同？ | 不重做判釋，把分散的成果整理成「哪件先查、證據是什麼、缺什麼、下一步做什麼」 |

### 6. 補形成期間雨量

**為什麼**：每張事件卡都掛著「形成期間雨量：尚未取得」的缺口。

**步驟**

1. 到 CWA 歷史雨量查詢（<https://rdc28.cwa.gov.tw/TDB/public/precipitation_statistics>），查馬太鞍溪上游附近測站 2025-07-20～21 的 24 小時累積雨量與最大時雨量。
2. 填進 `data/raw/observations.csv` 的 `bl071` 那一列：`rain_24h_mm`、`rain_max_hourly_mm`，`source` 欄註明測站與查詢網址。
3. 在 `code/` 底下跑 `python -m pipeline.events.build` 與 `python -m pipeline.attribution.annotate`。

**完成標準**：事件卡的雨量缺口消失；清冊的成因敘述會自動帶出雨量。
